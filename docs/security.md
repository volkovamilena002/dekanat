# Безопасность

Требования ТЗ и как они выполнены.

## 1. Студент видит только свои данные
- Все запросы к БД проходят через Data Access Layer (`src/lib/dal/`). Функции DAL **не принимают
  id студента** снаружи: они сами берут текущего пользователя из сессии и добавляют условие
  `student_id = <текущий>` в каждый запрос.
- Если запись принадлежит другому студенту, запрос возвращает пусто → страница отдаёт 404
  (настоящий HTTP-статус, не «Не найдено» со статусом 200). Подставить чужой id заявки в адрес бесполезно.
- Разделы сотрудника проверяют роль на сервере (`requireStaff()`), а не только скрывают кнопки.
- Server Actions заново проверяют сессию и роль — клиенту не доверяем.

## 2. Пароли не хранятся в открытом виде
- Хеш argon2id (`@node-rs/argon2`) с солью. Сравнение — `verify()` из библиотеки.
- При неверном логине выполняется фиктивная проверка хеша, чтобы по времени ответа
  нельзя было понять, существует ли логин. Сообщение об ошибке одинаковое.
- Ограничение попыток входа: не более 5 неудачных попыток за 15 минут на логин и на IP.

## 3. Сессии
- После входа генерируется случайный 256-битный токен, в cookie `dk_session`
  (`HttpOnly`, `Secure` в продакшене, `SameSite=Lax`, срок 7 дней).
- В БД хранится только SHA-256 от токена: утечка таблицы сессий не даёт войти.
- Выход удаляет сессию в БД и cookie.

## 4. Ключи и пароли сервисов не в коде и не в браузере
- Все секреты (сейчас это строка подключения к БД) — только в переменных окружения на сервере
  (`.env.local` не коммитится, есть `.env.example` без значений).
- Внешние ИИ-сервисы в прототипе не используются. Если появятся — только через серверный
  обработчик, ключ в браузер не попадает. Переменные с префиксом `NEXT_PUBLIC_` для секретов запрещены.

## 5. Целостность данных
- Запись на электив: строка электива блокируется (`SELECT … FOR UPDATE`) на время проверки
  мест и лимита — два студента не займут последнее место одновременно. Сервер проверяет
  срок записи, лимит и курс студента, даже если кнопку в браузере «разблокировать» вручную.
- Изменение пары сотрудником: строка пары блокируется, пересечения по группе, аудитории
  и преподавателю проверяются в той же транзакции, что и запись + уведомление.
- Одногруппники в демо-данных нужны только для реалистичных счётчиков мест: у них хеш
  случайного пароля, который нигде не сохранён, — войти под ними нельзя.

## 6. Прочее
- Валидация всех форм на сервере (zod).
- Заголовки безопасности: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy`, `Permissions-Policy`.
- Защита от CSRF у Server Actions встроена в Next.js (проверка Origin).
- Только вымышленные данные, к реальным системам вуза прототип не подключён.

## Автотесты
`npm run test:e2e` проверяет всё перечисленное автоматически (`e2e/security.spec.ts`): закрытые
страницы без входа, чужая заявка и документ → 404, разделение ролей, флаги cookie, недействительность
cookie после выхода, одинаковая ошибка входа, блокировка после 5 попыток, заголовки, отсутствие
хешей и строк подключения в HTML. Плюс серверная защита записи на элективы (`e2e/electives.spec.ts`).

## Как проверить вручную
1. Войти студентом A, открыть заявку, скопировать адрес `/requests/<id>`.
2. Выйти, войти студентом B, открыть тот же адрес → «Не найдено».
3. Студентом открыть `/staff` → перенаправление, доступа нет.
4. В БД в таблице `users` поле `password_hash` начинается с `$argon2id$`.
5. Студентом на странице элективов включить заблокированную кнопку «Мест нет» через DevTools
   и нажать → сервер ответит «Места закончились».
